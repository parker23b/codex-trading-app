# Audit status

This document is an audit log for InvestMate findings, evidence gaps, and follow-up actions. It is not a requirements spec; requirements live in `docs/spec/`.

## Current readiness blockers

InvestMate is **not ready for live or demo trading** while these blockers remain open. Startup/reload runtime-loop duplication now has backend lease evidence, but remaining P1 behaviours still need route/backend/frontend test evidence proportionate to their risk before any live/demo trading.

### Missing evidence blocking confidence

- Route/API: no HTTP `TestClient` suite proves passive no-write behaviour, active-read side effects, route response contracts, or mutation error/audit preservation. `/testing/*` production gating now has router-registration/direct-route regression evidence, but no broad HTTP route harness exists.
- Frontend: no behavioural test harness proves degraded, unknown, stale, fallback, mutation-error, enum-parity, passive-read, or test-only-control states; no static/import guard proves production code is free of mock/demo/fallback backend data.
- Audit trail: many tests globally mock durable `DomainEventService.record_event`, so audit persistence is not proven for lifecycle and mutation success paths.
- Security: backend auth-policy tests now prove mutation/test-only endpoints and write-on-read refresh routes require an operator identity in production-like operation, but no HTTP `TestClient` suite exists and no redaction tests prove broker/account/secrets are excluded from logs, domain events, and API errors.
- Database/supply chain: no migration drift tests, Python lockfile/constraints evidence, or dependency-vulnerability CI gate proves a reproducible production dependency/database state.
- Product/docs: README now documents safe local usage, setup prerequisites, expected degraded startup states, route-reference handoff, and current limitations; automated docs checks are still not part of CI.
- Matrix completeness: 68 boundary/surface P0/P1 spec IDs are still missing from explicit matrix rows or grouped notes.

## Severity definitions

- P0: Could allow unsafe trading, unbounded risk, unauditable broker action, unmanaged open exposure, hidden state corruption, or false readiness for a safety-critical control.
- P1: Violates or obscures a documented invariant, breaks a core audit flow, weakens P0/P1 evidence, misleads the operator/auditor, hides degraded state, mutates unexpectedly, or weakens auditability.
- P2: Documentation drift, incomplete central tracking, ambiguous ownership, confusing terminology, missing evidence structure, or maintainability issue outside an immediate P0/P1 safety path.
- P3: Minor cleanup or editorial issue. The spec set currently uses P0-P2 for requirement severity; P3 is available for audit-log housekeeping if needed.
