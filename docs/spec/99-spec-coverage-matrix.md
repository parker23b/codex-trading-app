# Spec coverage matrix

This matrix tracks whether important spec behaviours are supported by code, backend tests, route tests, frontend tests, full-stack/e2e tests, and documentation. It is not a substitute for tests. It is an audit index used to identify missing evidence, stale assumptions, and next review tasks.

A row should not be marked High overall if the behaviour includes frontend/operator display requirements and frontend evidence is missing, unless the notes explicitly scope the confidence to backend-only behaviour.

## Confidence labels

- High: implementation path and direct behavioural tests support the behaviour at the required layer.
- Medium: implementation path appears to support the behaviour, but tests are partial, indirect, backend-only, or missing at one required layer.
- Low: behaviour is inferred from code names, partial traces, docs, or incomplete evidence.
- Unknown: not enough evidence.
- Needs audit: route/code/test trace is required before confidence can be assigned.
- Needs test: expected behaviour is understood but automated test evidence is missing.

Confidence should be scoped. Backend confidence, route confidence, frontend confidence, and overall confidence may differ.

## Verification levels

- `NOT_TESTED`: no meaningful automated evidence identified.
- `CONSTRUCTION_ONLY`: tests only object construction/import/configuration.
- `UNIT_VERIFIED`: isolated unit behaviour tested.
- `SERVICE_VERIFIED`: service behaviour tested with meaningful fakes/session state.
- `ROUTE_VERIFIED`: API route behaviour, response shape, errors, and side effects tested.
- `FRONTEND_VERIFIED`: frontend component/API-client behaviour tested.
- `FULL_STACK_VERIFIED`: backend route/service/persistence and frontend consumption tested together through realistic fixtures or integration.
- `E2E_VERIFIED`: browser-level or true end-to-end behaviour tested through the UI.
- `NOT_APPLICABLE`: test evidence is not applicable, usually for pure terminology/product identity rows.

## Matrix maintenance rules

- Every P0/P1 invariant should appear in this matrix or be intentionally deferred with a note.
- Every P0 row requires direct behavioural backend evidence and, where operator-facing, route/frontend evidence.
- Every P1 row requires behavioural evidence where practical, especially for read-only guarantees, UI truthfulness, broker boundaries, risk confidence, and lifecycle transitions.
- A row should not be upgraded to High overall without named test evidence or an explicit non-test rationale.
- Backend-only confidence must not be mistaken for full-stack confidence.
- Frontend/operator-facing behaviours require frontend evidence or must remain Medium/Low overall.
- Dict-shaped backend responses consumed by frontend should be marked Needs schema until modeled or documented.
- Every Low, Unknown, Needs audit, or Needs test P0/P1 row should have a Next action.
- New P0/P1 spec IDs should be added to this matrix when specs change.
- Boundary/control and surface-specific rows may be tracked individually or intentionally grouped under a parent invariant row, but grouped coverage must be stated explicitly in Notes rather than implied.
